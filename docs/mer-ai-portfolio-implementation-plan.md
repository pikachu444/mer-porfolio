# 메르AI 포트폴리오 구현 계획

메르 블로그를 근거로 모델 포트폴리오를 구성하는 시스템의 상세 설계 문서다.
전체 진행 상태와 현재 논의 항목은 [작업 목록](./mer-ai-portfolio-task-list.md)에서 관리한다.

각 항목의 `합의됨`, `논의 필요`, `완료 조건`을 기준으로 구현한다. 합의되지 않은 정책은
임의로 결정하지 않는다.

## 현재 운영 정책 보정 (2026-07-14)

전체 비중 리밸런싱 주기는 7일(주 1회)로 운영한다. 메르의 논지 연속성을 보존하기 위해
기준일이 없는 최초·수동 리밸런싱과 요약 캐시 업그레이드에는 최근 14일의 원문·요약을
분석 근거로 사용한다. 아래 과거 완료 기록의 `14일` 표기는 당시 정책 또는 데이터 복구
범위를 뜻하며 현재 실행 코드는 이 보정 정책을 따른다.

## 목표

블로거가 실제 매수, 보유, 매도했다고 밝힌 종목을 우선 반영한다. 블로그에서 긍정적으로
분석한 종목이나 섹터를 근거로 AI가 종목 또는 ETF를 제한적으로 추가하여 모델 포트폴리오를
구성한다.

블로거의 직접 판단과 AI의 추론은 반드시 구분하여 표시한다.

## 확인된 현재 문제

- 현재 `기존보유`는 블로거의 실제 보유가 아니라 기존 모델 포트폴리오의 active 상태를 뜻한다.
- 현재 검증은 종목명, 티커 또는 코드가 원문에 등장하는지만 확인한다.
- 종목 주변의 `보유`, `매수`, `편입` 단어만으로 직접 판단을 분류하여 문맥 오인 가능성이 있다.
- AI가 섹터 분석만으로 추가한 종목과 블로거가 직접 판단한 종목이 화면에서 구분되지 않는다.
- 비중 변경 근거와 판단 날짜가 충분히 기록되지 않는다.

## 상세 계획

### 1. 포트폴리오 판단 데이터 구조 정의

**목적:** 블로거의 직접 판단과 AI의 추론을 상태 파일에서 구별한다.

**합의됨**

출처와 행동을 하나의 값으로 합치지 않고 별도 필드로 관리한다.

| 필드 | 허용값 |
|---|---|
| `판단 주체` | `메르`, `AI` |
| `판단` | `매수`, `보유`, `비중확대`, `비중축소`, `매도` |
| `근거` | `직접 발언`, `종목 분석`, `섹터 분석`, `이전 판단 유지` |

화면에는 `메르 · 매수`, `AI · 보유`, `AI · 매도 제안`처럼 표시한다.

**합의됨: Watchlist 분리**

Watchlist는 아직 모델 포트폴리오에 편입하지 않았지만 이후 변화를 추적할 대상을 관리한다.
포트폴리오와 Watchlist를 분리하여 성과 계산과 관심 대상 추적을 섞지 않는다.

| 목록 | 포함 대상 | 목표 비중 | 포트폴리오 성과 계산 |
|---|---|---|---|
| 모델 포트폴리오 | 실제 편입 종목 및 ETF | 있음 | 포함 |
| Watchlist | 관심 종목, 섹터, ETF | 없음 | 제외 |
| 종료 포지션 | 과거 편입 후 제외된 종목 및 ETF | 과거 값 보존 | 종료 성과 보존 |

Watchlist에도 판단 주체를 기록한다.

| 예시 | 판단 주체 | 대상 유형 | 근거 |
|---|---|---|---|
| 특정 기업 | `메르` | `종목` | 블로거가 관심 종목으로 직접 언급 |
| 우주 데이터센터 | `메르` | `섹터` | 블로거가 관심 산업으로 직접 언급 |
| 반도체 ETF | `AI` | `ETF` | 긍정 섹터 분석을 추적하기 위한 AI 제안 |

Watchlist는 매수 추천 목록이 아니다. 화면에서도 모델 포트폴리오와 별도 영역으로 표시한다.

Watchlist 편입은 특정 문자열의 존재 여부만으로 결정하지 않는다. 블로거는 같은 의미를
다양한 표현으로 작성할 수 있으므로 LLM이 글의 문맥을 읽고 관심 대상인지 판단한다.

Watchlist 편입 기준:

- LLM이 블로그의 전체 맥락을 읽고 긍정적으로 평가한 종목, 섹터, ETF를 Watchlist에 넣는다.
- 특정 단어가 포함됐는지 여부로 기계적으로 편입하지 않는다.
- Watchlist 편입은 모델 포트폴리오 매수를 의미하지 않는다.
- 메르의 직접 관심과 AI의 긍정적 해석을 구분하여 표시한다.

Watchlist 항목은 우선 유지한다. 최신 근거일로부터 `1년`이 지나면 자동 삭제하지 않고
`재검토 필요` 상태로 전환한다. 이후 LLM이 최신 블로그 맥락을 검토하여 유지 또는 종료를
제안한다.

Watchlist 항목에는 최소한 다음 이력을 기록한다.

| 필드 | 의미 |
|---|---|
| `관심 등록일` | Watchlist에 처음 들어온 날짜 |
| `최신 근거일` | 관련 근거가 마지막으로 갱신된 날짜 |
| `Watchlist 유지 기간` | 관심 등록일부터 현재 또는 종료일까지의 기간 |
| `포트폴리오 편입일` | Watchlist에서 모델 포트폴리오로 이동한 날짜. 미편입이면 비워 둠 |
| `Watchlist 종료일` | 편입, 배제 또는 정책상 종료된 날짜 |
| `상태` | `관심`, `재검토 필요`, `포트폴리오 편입`, `종료` |

**합의됨: 내부 JSON 필드명**

내부 JSON 필드명은 영문 `snake_case`로 통일한다. 상태 파일 최상위 목록은 다음 이름을
사용한다.

| 필드 | 의미 |
|---|---|
| `portfolio` | 현재 모델 포트폴리오 |
| `watchlist` | 관심 대상 |
| `closed_positions` | 종료 포지션 |
| `decision_history` | 실행별 판단 이력 |
| `last_rebalanced_date` | 마지막 전체 비중 재조정일 |

종목, ETF, 섹터를 식별하는 공통 필드는 다음 이름을 사용한다.

| 필드 | 의미 |
|---|---|
| `name` | 종목, ETF 또는 섹터 이름 |
| `code` | 종목 코드 또는 티커. 섹터처럼 코드가 없으면 비워 둠 |
| `market` | 시장 구분 |
| `asset_type` | `stock`, `etf`, `sector`, `cash` |

판단과 비중에 관한 필드는 다음 이름을 사용한다.

| 필드 | 의미 |
|---|---|
| `decision_actor` | 판단 주체: `메르`, `AI` |
| `action` | 판단: `매수`, `보유`, `비중확대`, `비중축소`, `매도` |
| `basis` | 근거: `직접 발언`, `종목 분석`, `섹터 분석`, `이전 판단 유지` |
| `decision_date` | 판단일 |
| `evidence_posts` | 근거 글 목록. 각 항목에 제목, URL, 게시일을 기록 |
| `source_mentioned` | 원문에 종목, ETF 또는 섹터가 직접 등장했는지 여부 |
| `previous_weight` | 변경 전 목표 비중 |
| `proposed_weight` | 제안 목표 비중 |
| `weight_source` | 비중 출처: `메르 직접 발언 기반`, `AI 제안` |
| `change_reason` | 판단 또는 비중 변경 이유 |
| `allocation_role` | 포트폴리오 역할: `core`, `satellite`, `risk`, `defensive`, `watch` |

`evidence_posts`의 각 항목은 다음 필드를 사용한다.

| 필드 | 의미 |
|---|---|
| `title` | 근거 글 제목 |
| `url` | 근거 글 URL |
| `published_date` | 근거 글 게시일 |

Watchlist 이력 필드는 다음 이름을 사용한다.

| 필드 | 의미 |
|---|---|
| `watchlist_entry_date` | 관심 등록일 |
| `latest_evidence_date` | 최신 근거일 |
| `watchlist_duration_days` | Watchlist 유지 기간 |
| `portfolio_entry_date` | 포트폴리오 편입일 |
| `watchlist_closed_date` | Watchlist 종료일 |
| `status` | `관심`, `재검토 필요`, `포트폴리오 편입`, `종료` |

**완료 조건**

- 상태 파일 스키마가 문서에 확정되어 있다.
- 신규 스키마 파싱 테스트가 있다.

**구현 완료**

- `portfolio_schema.py`에 v2 상태 스키마와 JSON 파서를 추가했다.
- 기존 `output/portfolio_state.json`은 8번 마이그레이션 전까지 변경하지 않는다.
- `tests/test_portfolio_schema.py`에 정상 파싱, 허용하지 않는 판단 주체, 변경 이유 누락,
  Watchlist 비중 혼입 차단 테스트를 추가했다.
- 검증 결과: `PYTHONUTF8=1 python -m unittest discover -s tests -v` 실행 시 전체 `7`개
  테스트가 통과했다.

### 2. `메르` 직접 판단 인정 기준 정의

**목적:** 블로거 본인의 행동과 글에 등장한 일반 사례를 구별한다.

**합의됨**

- `메르` 판단에는 근거 글 제목, URL, 게시일이 반드시 필요하다.
- 새 글에서 다시 언급되지 않았다면 메르 판단일을 임의로 갱신하지 않는다.
- "리커전이 보유한 데이터" 같은 문장을 블로거의 주식 보유로 분류하면 안 된다.
- `메르 · 매수`, `메르 · 보유`, `메르 · 매도` 여부는 특정 문자열 규칙이 아니라 LLM이
  글의 전체 문맥을 읽고 판단한다.
- 코드는 메르의 투자 판단을 다시 수행하지 않는다.
- 메르가 비중을 직접 언급했는지도 LLM이 글의 전체 문맥을 읽고 판단한다.
- 메르의 직접 비중 발언을 위한 별도 필드는 추가하지 않는다. 모델 포트폴리오에서 실제로
  사용할 목표 비중은 `proposed_weight`에 기록하고, 출처는 `weight_source`, 근거 글은
  `evidence_posts`, 결정 이유는 `change_reason`으로 추적한다.
- 메르가 비중을 직접 언급했더라도 모델 포트폴리오의 목표 비중과 다를 수 있다.

**합의됨: 직접 판단 인정 및 제외 사례**

| 원문 의미 | 분류 |
|---|---|
| 메르가 본인이 특정 종목을 샀다고 밝힘 | `메르 · 매수` |
| 메르가 본인이 특정 종목을 보유 중이라고 밝힘 | `메르 · 보유` |
| 메르가 본인이 특정 종목을 팔았다고 밝힘 | `메르 · 매도` |
| 타인이나 기업이 종목 또는 데이터를 보유함 | 메르 판단 아님 |
| 특정 종목을 긍정적으로 분석함 | 메르 직접 판단 아님. AI 추론 후보 |
| 특정 섹터의 전망을 긍정적으로 분석함 | 메르 직접 판단 아님. AI 추론 후보 |

Gemini 프롬프트에는 위 사례를 포함한다. 코드는 문맥을 다시 해석하지 않고, `메르` 판단에
필요한 구조적 근거가 포함됐는지만 검사한다.

**완료 조건**

- 행동별 인정 및 제외 예시가 문서화되어 있다.
- 오분류 방지 테스트가 있다.

**구현 완료**

- 직접 판단 인정 및 제외 사례를 문서화했다.
- `portfolio_schema.py`에서 `메르` 판단은 `직접 발언` 근거, 근거 글, 원문 등장 여부를
  반드시 포함하도록 구조 검증을 추가했다.
- 코드는 블로그 문맥을 다시 해석하지 않는다. LLM의 분류 결과에 명백한 구조 모순이 있는
  경우만 차단한다.
- `tests/test_portfolio_schema.py`에 직접 발언 근거 누락, 근거 글 누락, 원문 등장 여부 오류
  차단 테스트를 추가했다.
- 검증 결과: `PYTHONUTF8=1 python -m unittest discover -s tests -v` 실행 시 전체 `10`개
  테스트가 통과했다.

### 3. `AI · 매수` 허용 조건 정의

**목적:** 블로그를 근거로 AI가 모델 포트폴리오를 확장할 수 있는 범위를 정한다.

**합의됨**

- 글에 등장한 종목을 AI가 제안할 수 있다.
- 긍정 섹터를 근거로 AI가 종목 또는 ETF를 제한적으로 제안할 수 있다.
- AI의 제안을 블로거의 직접 추천처럼 표시하면 안 된다.
- 원문에 종목이 등장하지 않았다면 그 사실을 표시한다.
- `메르 · 매수`는 모델 포트폴리오에 즉시 편입한다.
- `AI · 매수`도 LLM이 블로그 근거상 투자 매력이 충분하다고 판단하면 모델 포트폴리오에
  즉시 편입한다.
- 긍정적으로 평가하지만 즉시 편입할 수준은 아니라고 판단한 종목, 섹터, ETF는 Watchlist에
  넣는다.
- `메르 · 매수`, `AI · 매수`, Watchlist 항목은 보고서와 HTML에서 명확히 구분한다.
- 블로그에 긍정적인 섹터 분석만 있고 특정 종목이 직접 등장하지 않은 경우에도, LLM은
  대표 종목, ETF 또는 둘 다 `AI · 매수`로 즉시 편입할 수 있다.
- 원문에 직접 등장하지 않은 종목이나 ETF를 편입하면 `원문 종목 등장 없음`과 AI가 선택한
  이유를 보고서와 HTML에 표시한다.

**완료 조건**

- 허용 및 차단 규칙이 확정되어 있다.
- 원문 직접 등장 여부가 상태 파일과 보고서에 표시된다.

**구현 진행**

- `portfolio_schema.py`에서 원문에 등장하지 않은 신규 `AI · 매수`는 `섹터 분석` 근거와
  근거 글을 반드시 포함하도록 구조 검증을 추가했다.
- 원문에 등장하지 않은 종목이라도 이미 편입된 뒤 `AI · 보유`, `이전 판단 유지`로 판단하는
  것은 허용한다.
- `tests/test_portfolio_schema.py`에 원문 미등장 신규 AI 매수의 정상, 근거 유형 오류, 근거 글
  누락, 이후 보유 유지 사례를 추가했다.
- 검증 결과: `PYTHONUTF8=1 python -m unittest discover -s tests -v` 실행 시 전체 `13`개
  테스트가 통과했다.
**구현 완료**

- 6번 Gemini 프롬프트 개편에서 원문 직접 등장 여부를 구조화 판단 JSON에 연결하고, 2차
  보고서 프롬프트에 원문 미등장 AI 제안 표시 지시를 추가했다.
- 상태 JSON과 Markdown 보고서 연결이 완료됐다. HTML 화면 표시는 9번에서 이어서 구현한다.

### 4. 기존 포지션 유지 및 종료 규칙 정의

**목적:** 종목이 새 글에서 사라졌을 때 임의 제거를 방지한다.

**합의됨**

- 새 글에 다시 나오지 않았다는 이유만으로 종목을 자동 제거하지 않는다.
- `메르 · 매도`는 현재 포트폴리오에서 제외하고 종료 이력을 보존한다.
- `AI · 매도`도 LLM이 블로그 맥락상 기존 투자 근거가 훼손됐다고 판단하면 현재
  포트폴리오에서 제외하고 종료 이력을 보존한다.
- 별도의 사용자 승인 절차를 두지 않는다. 이 시스템은 GitHub Actions에서 자동 실행된다.
- 긍정 근거가 약해졌지만 매도 수준은 아니라면 `비중축소`를 제안한다.
- 종료 이력에는 판단 주체, 종료일, 근거 글 제목과 URL, 종료 이유, 종료 직전 비중, 성과를
  기록한다.
- 포트폴리오 종목에는 만료 기간을 두지 않는다.
- 시간 경과만으로 포트폴리오 종목을 제거하지 않는다.
- 이후 블로그 글을 읽은 LLM이 `유지`, `비중축소`, `매도` 중 하나를 판단한다.
- Watchlist는 아직 포트폴리오에 편입하지 않은 관심 대상을 추적한다. 포트폴리오 종목을
  Watchlist로 이동하는 상태 전이는 두지 않는다.
- 최신 근거일로부터 `1년` 후 `재검토 필요`로 전환하는 규칙은 Watchlist에만 적용한다.

**완료 조건**

- 유지, 검토, 종료 상태 전이가 구현되어 있다.
- 상태 전이 테스트가 있다.

**구현 완료**

- `portfolio_schema.py`에 v2 상태에 구조화 판단을 적용하는 `apply_portfolio_decisions`를
  추가했다.
- 새 판단에 포함되지 않은 기존 포지션은 그대로 유지한다.
- `비중축소` 판단은 현재 포트폴리오 안에서 비중을 갱신한다.
- `매도` 판단은 현재 포트폴리오에서 종목을 제거하고 `closed_positions`에 종료일, 종료
  이유, 종료 직전 비중, 종료 성과를 보존한다.
- 포트폴리오와 Watchlist 사이의 이동 전이는 두지 않는다.
- `tests/test_portfolio_schema.py`에 미언급 종목 유지, 비중축소, 종료 이력 보존, 미보유 종목
  매도 차단 테스트를 추가했다.
- 검증 결과: `PYTHONUTF8=1 python -m unittest discover -s tests -v` 실행 시 전체 `17`개
  테스트가 통과했다.

### 5. 비중 제안 원칙 정의

**목적:** 블로그 근거 없이 목표 비중이 흔들리는 문제를 막는다.

**합의됨**

- 블로거가 직접 비중을 제시했는지는 LLM이 전체 문맥에서 판단하고, 목표 비중의 출처와
  근거 글에 반영한다. 직접 비중만을 위한 별도 필드는 두지 않는다.
- 블로거가 비중을 직접 제시하지 않았다면 LLM이 블로그에서 읽은 확신도와 모델
  포트폴리오 전체 구성을 함께 고려하여 비중을 제안한다.
- 새로운 근거가 없으면 기존 판단과 기존 비중을 임의로 바꾸지 않는다.
- 비중 변경 시 이전 비중, 제안 비중, 변경 이유, 근거 글을 기록한다.
- 비중의 출처는 `메르 직접 발언 기반`과 `AI 제안`으로 구분한다.
- 신규 편입이나 비중확대로 합계가 달라질 때 기존 종목과 현금 비중을 재배분하는 것도
  `AI 제안`에 포함한다.
- AI가 비중을 변경하면 해당 종목 자체의 근거 변화인지, 전체 포트폴리오 재배분인지 이유를
  함께 기록한다.
- 새 글이 있으면 매번 분석하여 포트폴리오 판단과 Watchlist를 갱신한다.
- 새 글이 없는 날에도 매일 주가, 수익률, 그래프, HTML, Telegram 메시지를 갱신한다.
- 새 글이 없는 날에는 LLM 투자 판단을 새로 만들지 않고, 포트폴리오 종목, 판단, 목표 비중,
  Watchlist를 변경하지 않는다.
- 전체 포트폴리오 비중 재조정은 마지막 리밸런싱 이후 `7일`이 경과했을 때 수행한다.
- 마지막 리밸런싱 이후 `7일`이 경과했더라도 누적 신규 글이 없으면 전체 비중 재조정을
  실행하지 않는다. 다음 신규 글이 들어오는 날까지 미룬다.
- 일반 분석에서는 기존 종목 비중을 기본적으로 유지한다.
- 일반 분석 중 신규 종목을 즉시 편입할 때는 현금 비중에서 우선 배정한다.
- 신규 종목을 즉시 편입해야 하지만 현금이 부족하면 기존 포트폴리오 종목의 비중을 균등한
  비율로 축소하여 필요한 비중을 확보한다.
- 현금 사용과 기존 종목 축소를 포함한 즉시 재배분도 변경 이유를 기록한다.

**폐기한 임시값**

아래 숫자는 블로그 분석이나 사용자 합의에서 도출되지 않았으므로 정책으로 사용하지 않는다.

| 항목 | 폐기한 값 |
|---|---:|
| 단일 종목 최대 | 15% |
| 신규 종목 최대 | 10% |
| 단순 직접언급 신규 종목 | 3~5% |
| 현금 최소 | 10% |

**합의됨: 리밸런싱 기준일 저장**

- 상태 파일 최상위에 `last_rebalanced_date`를 저장한다.
- 전체 포트폴리오 비중 재조정을 실제로 수행한 날에만 값을 갱신한다.
- 일반 분석이나 신규 종목 즉시 편입 때는 값을 갱신하지 않는다.
- `scheduled` 실행은 이 날짜로부터 `7일` 경과 여부를 확인한다.
- 누적 신규 글이 없으면 리밸런싱을 미루고 날짜도 갱신하지 않는다.

**완료 조건**

- Gemini 프롬프트에 반영할 비중 원칙이 확정되어 있다.
- 비중 변경 이유 누락을 감지하는 테스트가 있다.

**구현 진행**

- 상태 파일 최상위에 `last_rebalanced_date`를 추가했다.
- `apply_portfolio_decisions`는 일반 분석과 신규 종목 즉시 편입에서 리밸런싱 기준일을
  유지하고, 전체 비중 재조정일이 명시된 경우에만 갱신한다.
- 구조화 판단에 `change_reason`이 없거나 비어 있으면 차단한다.
- `tests/test_portfolio_schema.py`에 일반 분석 시 기준일 유지, 명시적 전체 재조정 시 기준일
  갱신, 변경 이유 누락 차단 테스트를 추가했다.
- 검증 결과: `PYTHONUTF8=1 python -m unittest discover -s tests -v` 실행 시 전체 `20`개
  테스트가 통과했다.
**구현 완료**

- 6번 Gemini 프롬프트 개편에서 비중 원칙과 `last_rebalanced_date`를 1차 판단 입력 계약에
  연결했다.
- 검증 결과는 6번 구현 완료 기록에 함께 남긴다.

### 6. Gemini 요청 프롬프트 개편

**목적:** LLM이 출처, 판단, 날짜, 근거 글, 비중 변경 이유를 구조적으로 출력하게 한다.

**합의됨**

Gemini 호출을 두 단계로 분리한다.

```text
1차 호출: 포트폴리오 판단
블로그 글 + 현재 모델 포트폴리오 + Watchlist + 리밸런싱 정보
→ 구조화된 판단 JSON

2차 호출: 사용자용 보고서 작성
블로그 글 + 1차 판단 JSON
→ 사람이 읽는 Markdown 보고서
```

1차 판단 JSON을 포트폴리오 상태 갱신의 기준 데이터로 사용한다. Markdown 보고서를 다시
파싱하여 상태를 갱신하는 현재 방식은 교체한다.

1차 판단 JSON은 매 실행마다 저장한다. 이후 판단이 바뀐 이유와 과거 이력을 추적할 수 있어야
한다.

HTML, Telegram, Markdown 보고서는 동일한 판단 JSON을 기준으로 생성한다.

매 실행에서 LLM은 최신 블로그 글과 기존 포트폴리오, 기존 Watchlist를 함께 읽고 기존 항목의
유지, 확대, 축소, 매도 여부를 다시 판단한다. 판단마다 이번 판단의 직접 근거가 된 글 제목,
URL, 게시일을 기록한다.

글 수집과 전체 비중 리밸런싱은 분리한다.

| 실행 | 입력 글 범위 | 처리 |
|---|---|---|
| 신규 글 있음 | 매일 수집한 신규 글 | 포트폴리오 판단, Watchlist 갱신, 필요한 즉시 변경 |
| 신규 글 없음 | LLM 분석 없음 | 주가, 수익률, 그래프, HTML, Telegram 갱신. 포트폴리오 변경 없음 |
| `주간(7일)` 리밸런싱 | 마지막 리밸런싱 이후 누적 수집한 글 전체 | 최신 흐름 종합, 전체 비중 재조정 |

`7일`은 최소 재조정 간격이다. 기간이 지났더라도 새 근거가 없으면 비중을 흔들지 않는다.
기준일이 없는 최초·수동 리밸런싱은 최근 `14일`의 원문·요약을 사용한다.

수집한 글은 기존 글 저장소에 계속 누적한다. 리밸런싱을 위해 매일 과거 글 전체를 다시
수집하지 않는다.

사용자 화면에서는 `주간 리밸런싱` 같은 기술 용어를 제목으로 강조하지 않는다. 기존
`메르AI 포트폴리오 분석` 제목을 유지하고, 전체 비중 조정이 발생한 날에만 실행 유형을
`정기 분석 · 포트폴리오 비중 조정`으로 표시한다. HTML은 하나의 대시보드를 유지하고,
Telegram 메시지와 Markdown 보고서도 동일한 사용자용 명칭을 사용한다.

별도의 종목별 또는 섹터별 폴더 구조를 만들지 않는다. 실행별 판단 JSON을 저장하여 판단
이력을 보존한다.

두 호출은 하나의 실행 단위로 취급한다. 1차 판단 JSON 생성은 성공했지만 2차 Markdown
보고서 작성이 실패하면 신규 판단 JSON과 포트폴리오 상태를 반영하지 않고 이전 보고서를
유지한다. 내부 상태와 사용자에게 보이는 보고서가 서로 어긋나지 않아야 한다.

실패 처리는 정상 흐름을 대신하는 수단이 아니다. 전체 구현 품질 원칙은 저장소의
`AGENTS.md`를 따른다.

1차 판단 JSON은 최소한 다음 정보를 포함해야 한다.

| 필드 |
|---|
| 종목 |
| 판단 주체 |
| 판단 |
| 판단일 |
| 이전 비중 |
| 제안 비중 |
| 비중 출처 |
| 근거 |
| 원문 종목 등장 여부 |
| 근거 글 제목 및 URL |
| 변경 이유 |

**합의됨: 1차 판단 JSON 최상위 구조**

1차 호출은 전체 상태 파일을 다시 만들지 않고 이번 실행에서 적용할 판단만 출력한다.

```json
{
  "analysis_date": "2026-06-01",
  "run_type": "regular",
  "portfolio_decisions": [],
  "watchlist": []
}
```

- `run_type`은 `regular`, `rebalance` 중 하나를 사용한다.
- `portfolio_decisions`에는 기존 종목 유지, 확대, 축소, 매도 및 신규 편입 판단을 기록한다.
- `watchlist`에는 이번 분석 후 유지할 관심 대상 목록을 기록한다.
- 각 포트폴리오 판단은 1번에서 확정한 공통 식별 필드와 `decision_actor`, `action`, `basis`,
  `decision_date`, `evidence_posts`, `source_mentioned`, `previous_weight`, `proposed_weight`,
  `weight_source`, `change_reason`을 사용한다.
- 상태 갱신은 1차 판단 JSON만 기준으로 수행한다.
- 2차 호출은 1차 판단 JSON을 입력받아 Markdown 보고서만 작성한다.

**완료 조건**

- `system_prompt.py`가 확정된 스키마를 요청한다.
- 샘플 응답 파싱 테스트가 있다.

**구현 완료**

- `system_prompt.py`에 구조화 판단용 `DECISION_SYSTEM_PROMPT`와 사용자용 보고서 작성용
  `REPORT_SYSTEM_PROMPT`를 추가했다.
- 1차 판단 요청은 현재 모델 포트폴리오, Watchlist, `last_rebalanced_date`, 블로그 글을
  입력받아 확정된 JSON 구조만 출력하도록 요청한다.
- 2차 보고서 요청은 검증된 판단 JSON과 블로그 글을 입력받아 Markdown 보고서만 작성한다.
- `portfolio_schema.py`에 1차 판단 JSON 파서 `parse_analysis_decision_json`을 추가했다.
- `analyze.py`에 두 호출을 순서대로 수행하는 `analyze_posts_structured`를 추가했다.
- 2차 보고서 작성이 실패하면 구조화 판단도 반환하지 않는다. 실제 상태 적용과 저장 경로
  전환은 8번 마이그레이션에서 함께 연결한다.
- `tests/test_portfolio_schema.py`, `tests/test_structured_analysis.py`에 샘플 판단 JSON 파싱,
  프롬프트 계약, 호출 순서, 부분 성공 차단 테스트를 추가했다.
- 검증 결과: `PYTHONUTF8=1 python -m unittest discover -s tests -v` 실행 시 전체 `26`개
  테스트가 통과했다.

### 7. 추천 검증 로직 개편

**목적:** `portfolio_validation.py`가 신규 분류 체계를 검증하게 한다.

**합의됨**

- `메르` 판단은 근거 글, URL, 판단일, 직접 발언 근거가 있어야 한다.
- 원문에 없는 AI 종목도 합의된 조건에 따라 허용할 수 있다.
- 허용된 경우 `AI`, `섹터 분석`, `원문 종목 등장 없음`을 표시한다.
- 명시적 근거가 없는 종목 제거를 차단한다.
- 근거 없는 비중 변경을 경고한다.
- 코드는 LLM의 투자 판단을 다시 수행하지 않는다.
- 코드는 필수 필드 누락, 허용값 위반, 날짜 및 URL 형식 오류처럼 구조적 문제만 검사한다.

**합의됨: 검증 수준과 실패 처리**

- 직접 발언의 진위는 코드가 판별하지 않는다. LLM이 전체 문맥을 읽고 판단한다.
- 코드는 필수 필드 누락, 허용값 위반, 날짜 및 URL 형식 오류, `메르` 판단인데 직접 발언
  근거가 없는 경우처럼 명백한 구조 오류만 검사한다.
- 구조 오류가 있는 LLM 출력은 상태에 반영하지 않고 차단한다.
- 기존 비중과 제안 비중이 다른데 `change_reason`이 없거나 근거 글이 비어 있으면 차단한다.
- 값은 모두 채워졌지만 비중 변화가 큰 경우에는 임의 기준 숫자로 경고하지 않는다.
- 기존 문자열 주변의 `보유`, `매수`, `매도` 같은 단어로 메르의 직접 판단을 추정하는
  후처리는 신규 구조화 판단 경로에서 사용하지 않는다.

**완료 조건**

- 신규 검증 규칙이 구현되어 있다.
- 정상, 차단, 경고 사례 테스트가 있다.

**구현 완료**

- `portfolio_validation.py`에 신규 구조화 판단 검증 진입점 `validate_structured_decisions`를
  추가했다.
- 신규 구조화 경로는 문자열 주변의 `보유`, `매수`, `매도` 단어로 직접 판단을 추정하지
  않는다.
- `portfolio_schema.py`에서 필수 필드, 허용값, ISO 날짜, HTTP(S) URL, 메르 직접 발언 근거,
  원문 미등장 신규 AI 매수 근거, 비중 변경 이유와 근거 글을 검사한다.
- 구조 오류는 차단한다. 임의 숫자 기준의 비중 변화 경고는 추가하지 않았다.
- 기존 Markdown 후처리는 8번 운영 경로 전환 전까지 레거시 호환용으로 남겨 둔다.
- `tests/test_portfolio_schema.py`에 정상 검증, URL 오류, 날짜 오류, 비중 변경 근거 누락 차단
  테스트를 추가했다.
- 검증 결과: `PYTHONUTF8=1 python -m unittest discover -s tests -v` 실행 시 전체 `30`개
  테스트가 통과했다.

### 8. 포트폴리오 상태 및 이력 마이그레이션

**목적:** 기존 상태 파일을 신규 판단 구조로 전환한다.

**합의됨**

- 과거 판단을 삭제하지 않는다.
- 현재 포트폴리오에서 제외된 종목은 종료 이력으로 보존한다.
- 기존 `기존보유` 값은 메르 직접 보유로 간주하지 않는다.
- 기존 포트폴리오 종목은 과거 데이터만으로 `메르`, `AI` 판단 주체를 억지로 추정하지 않는다.
- 기존 종목의 판단 주체는 우선 `미분류`로 보존한다.
- 이후 새 글 분석에서 LLM이 판단을 갱신하면 `메르` 또는 `AI`로 변경하고 근거 글과 날짜를
  기록한다.
- 신규 구조를 처음 적용할 때는 저장된 과거 글과 현재 포트폴리오 전체를 LLM에 전달하여
  한 번 재평가한다.
- 최초 재평가에서 각 기존 종목을 `메르`, `AI`, `매도` 중 하나로 다시 분류하고 근거 글과
  날짜를 기록한다.
- 최초 재평가 전까지는 기존 종목을 삭제하지 않고 `미분류` 상태로 보존한다.

**합의됨: 마이그레이션 중 `미분류` 처리**

- 기존 상태 파일에서 옮긴 포트폴리오 종목과 종료 이력에만 `decision_actor: 미분류`를 임시
  허용한다.
- Gemini의 신규 판단 JSON에는 `미분류` 출력을 허용하지 않는다.
- 최초 재평가가 끝나면 기존 종목도 `메르`, `AI`, `매도` 중 하나로 전환한다.
- 별도의 임시 필드는 추가하지 않는다.
- 기존 상태 파일에는 실제 전체 비중 조정일이 없으므로 `last_rebalanced_date`를 추정하지
  않고 `null`로 둔다.

**완료 조건**

- 마이그레이션 함수와 테스트가 있다.
- 기존 출력 파일을 읽어도 오류가 발생하지 않는다.

**구현 완료**

- `portfolio_schema.py`에 기존 `holdings` 구조를 신규 포트폴리오, 종료 이력 구조로 옮기는
  메모리 마이그레이션과 검증된 상태 파일 원자적 저장 함수를 추가했다.
- 과거 데이터로 판단 주체를 추정하지 않는다. 기존 활성 종목 10건과 종료 종목 4건은
  `미분류`로 보존하고, 실제 전체 비중 조정일도 근거가 없어 `null`로 둔다.
- 신규 Gemini 판단 JSON에는 `미분류`를 허용하지 않으며, 최초 재평가 결과를 적용하면
  기존 종목 판단과 Watchlist가 신규 구조로 갱신된다.
- 운영 중인 `output/portfolio_state.json`은 수정하지 않고 메모리에서 읽어 변환 가능함을
  확인했다.
- 검증 결과: `PYTHONUTF8=1 python -m unittest discover -s tests -v` 실행 시 전체 `37`개
  테스트가 통과했다.

### 9. HTML 보고서 개편

**목적:** 사용자가 블로거의 직접 판단과 AI의 해석을 화면에서 즉시 구별하게 한다.

**합의됨**

HTML에는 다음 내용을 표시한다.

- 현재 모델 포트폴리오
- Watchlist
- 신규 편입
- 비중 확대 및 축소
- 매도 및 종료 포지션
- 판단 주체와 판단
- 판단일
- 근거 글 링크
- 변경 이유
- 목표 비중과 비중 출처

표는 첫 화면에서 핵심 정보만 보여주고, 상세 근거는 펼쳐서 확인한다.

- 현재 모델 포트폴리오, Watchlist, 변경 내역, 종료 포지션에 동일한 펼침 구조를 적용한다.
- 각 행에 개별 `펼치기`, `접기` 버튼을 둔다.
- 각 표 상단에 `모두 펼치기`, `모두 접기` 버튼을 둔다.
- 표마다 전체 펼침 상태를 별도로 관리한다. 화면 전체를 한 번에 모두 펼치지 않는다.
- 모바일에서는 핵심 컬럼만 먼저 보여주고 나머지 정보는 상세 영역에서 확인한다.
- `메르` 판단과 `AI` 판단은 라벨과 색상으로 즉시 구분한다.
- 이번 실행에서 변경된 행은 시각적으로 구분한다.
- 근거 글 링크는 상세 영역에서 바로 열 수 있게 한다.
- 정보가 없을 때는 빈 상태를 명확히 표시한다.

기본 표 예시:

| 종목 | 판단 | 비중 | 편입일 | 수익률 | 최신 근거일 |
|---|---|---:|---|---:|---|
| Alcoa `AA` | `AI · 매수` | 8% | 2026-05-28 | +3.6% | 2026-05-28 |

상세 영역 예시:

```text
비중 출처: AI 제안
변경 이유: 보크사이트 공급 제한에 따른 알루미늄 수혜 추론
근거 글: 기니, 중국을 건드리나? 2 · 2026-05-27 · 원문 링크
원문 종목 등장: 없음
```

**구현 세부**

- 현재 포트폴리오 목표 비중은 종목별 도넛 차트로 표시한다.
- Watchlist는 목표 비중이 없으므로 도넛 차트에서 제외한다.
- 도넛 조각은 종목별 목표 비중을 나타낸다.
- 도넛 중앙에는 포트폴리오 종목 수와 현금 비중을 표시한다.
- 범례에는 종목명, 코드, 목표 비중, 판단 주체, 이번 실행의 변화량을 표시한다.
- 조각 hover 또는 클릭 시 판단, 근거, 최신 근거일을 확인할 수 있게 한다.
- 종목별 색상은 서로 명확히 구별되는 범주형 팔레트를 사용한다. 같은 계열의 유사 색상을
  연속해서 사용하지 않는다.
- 현금은 중립 색상으로 표시한다.
- `메르`, `AI` 구분은 색상에만 의존하지 않고 범례 라벨과 보조 표시를 함께 사용한다.
- 모바일에서는 도넛 아래에 범례를 세로로 배치한다.
- 현재 모델 포트폴리오 전체 수익률의 시간 흐름을 선 그래프로 표시한다.
- 전체 포트폴리오 비중 조정이 발생한 날짜는 수익률 선 그래프 위에 표시점을 남긴다.
- 표시점을 hover 또는 클릭하면 비중 조정 날짜와 주요 변경 내역을 확인할 수 있게 한다.
- 일반 분석일은 별도 표시점을 남기지 않는다.
- 종료 포지션은 선 그래프에 섞지 않고 별도 종료 포지션 표에서 확인한다.

**구현 세부: 대시보드 섹션 순서**

대시보드 섹션 순서:

1. 최근 분석 요약
2. 현재 모델 포트폴리오 도넛 차트
3. 현재 모델 포트폴리오 표
4. 이번 분석 변경사항
5. Watchlist
6. 포트폴리오 수익률 선 그래프
7. 종료 포지션
8. 전체 Markdown 보고서

그래프 종류, 색상, 섹션 순서는 사용자 정책 결정이 필요한 사항이 아니다. 위 구성을 기본값으로
구현하고, 실제 HTML 확인 과정에서 가독성 문제가 있으면 조정한다.

**결과 품질 기준**

- Telegram 메시지와 HTML은 메르 블로거의 직접 판단을 우선하여 보여준다.
- 메르 블로거가 직접 언급하지 않은 종목을 AI가 추론하여 제안한 경우에는 `AI` 판단임을
  명확히 표시한다.
- 모델 포트폴리오는 메르 블로거의 실제 보유 종목이 아니라 블로그 판단을 바탕으로 구성한
  모델 포트폴리오임을 명확히 표시한다.
- 사용자는 개발 구조를 알지 않아도 메시지만 읽고 신규 편입, 유지, 비중 변경, 종료와 그
  이유를 구별할 수 있어야 한다.

**완료 조건**

- 데스크톱 및 모바일 HTML에서 신규 정보가 표시된다.
- 기존 성과 그래프와 표가 정상 동작한다.

**구현 완료**

- HTML은 Markdown 표를 다시 해석하지 않고 검증된 포트폴리오 상태를 기준으로 현재 모델
  포트폴리오, 이번 변경, Watchlist, 종료 포지션을 표시한다.
- 화면 상단에 메르 블로거의 실제 보유 내역이 아니라는 점을 명시하고, 각 판단에 `메르`,
  `AI`, 마이그레이션 직후의 `미분류` 라벨을 표시한다.
- 각 표에서 상세 근거 글, 판단일, 비중 출처, 변경 이유, 원문 종목 등장 여부를 펼쳐서
  확인할 수 있다.
- 모바일 핵심 컬럼 표시, 목표 비중 도넛 차트, 포트폴리오 수익률 선 그래프를 유지했다.
- `tests/test_generate_dashboard.py`에 모델 포트폴리오 고지, 판단 주체, Watchlist, 근거 링크,
  펼침 구조 검증을 추가했다.
- 로컬 임시 파일의 브라우저 직접 열기는 브라우저 보안 정책으로 차단되었다. 실제 배포
  URL에서의 데스크톱 및 모바일 눈검사는 12번 통합 검증에서 수행한다.

### 10. 성과 추적 기준 개편

**목적:** 모델 포트폴리오의 편입 및 종료 성과를 일관되게 추적한다.

**합의됨**

- 동일 종목의 추천일별 중복 성과 행을 만들지 않는다.
- 종료 포지션은 삭제하지 않는다.
- 편입일, 종료일, 종료 근거, 수익률을 보존한다.
- 모델 포트폴리오 성과는 실제 매매처럼 계산한다.
- 신규 편입은 신규 매수, 비중확대는 추가 매수, 비중축소는 일부 매도, 매도는 전량 매도로
  기록한다.
- 비중 변경일의 가격을 기준으로 거래 이력을 남긴다.
- 현금 비중과 실현 손익을 함께 추적한다.
- 최초 편입 가격과 현재 비중만 곱하는 단순 계산 방식은 사용하지 않는다.
- 성과는 하나의 모델 포트폴리오 전체 수익률로 표시한다.
- `메르`, `AI` 구분은 개별 종목 판단의 출처를 설명하는 용도로만 사용한다. 별도 전략처럼
  성과를 분리하지 않는다.

**완료 조건**

- 성과 계산 규칙이 문서화되어 있다.
- 중복, 비중 변경, 종료 테스트가 있다.

**구현 완료**

- 신규 구조 활성화 시점부터 시작하는 모델 거래 원장을 추가했다. 과거 거래 가격과 비중 변경
  내역은 추정하여 복원하지 않는다.
- 신규 편입은 `신규 매수`, 비중 확대는 `추가 매수`, 비중 축소는 `일부 매도`, 매도는
  `전량 매도`로 기록한다.
- 각 스냅샷에는 현금, 투자 평가액, 전체 평가액, 전체 수익률, 실현 손익을 함께 기록한다.
- 기존 `portfolio_history.json` 운영 파일은 수정하지 않았다. 신규 원장의 실제 저장 연결은
  11번 실행 경로 교체에서 수행한다.
- `tests/test_model_ledger.py`에 신규 매수, 확대, 축소, 종료, 현금, 실현 손익, 거래 가격 누락
  차단 테스트를 추가했다.
- 검증 결과: `PYTHONUTF8=1 python -m unittest discover -s tests -v` 실행 시 전체 `41`개
  테스트가 통과했다.

### 11. Actions 실행 모드 정리

**목적:** 검증 실행이 실제 포트폴리오를 의도치 않게 변경하지 않도록 한다.

**현재 상태**

| 모드 | 역할 |
|---|---|
| `scheduled` | 신규 글 기반 모니터링 |
| `rebalance` | 최근 14일 글 기반 전면 재검토 및 상태 저장 |
| `test` | 상태 저장과 Telegram 전송 없이 전면 재검토 |

**합의됨**

| 모드 | 실행 방식 | 입력 | 상태 변경 | Telegram | 목적 |
|---|---|---|---|---|---|
| `scheduled` | 매일 자동 | 신규 글 및 최신 가격 | 신규 글이 있을 때만 판단 변경 | 실제 전송 | 일상 운영 및 매일 성과 갱신 |
| `rebalance` | 주 1회 자동 및 필요 시 수동 | 마지막 리밸런싱 이후 누적 글 | 있음 | 실제 전송 | 전체 목표 비중 재조정 |
| `verify` | GitHub Actions 수동 | 실제 운영 입력을 임시 상태에서 처리 | 없음 | 실제 전송 | HTML, PNG, Telegram 결과 검증 |
| `test` | 로컬 또는 CI | 고정 fixture 및 mock 응답 | 없음 | 없음 | API 키 없이 코드 테스트 |

- 기존 `adhoc` 이름은 `rebalance`로 변경한다.
- 자동 리밸런싱은 별도 Actions 스케줄로 분리하지 않는다. 매일 실행되는 `scheduled`가 마지막
  리밸런싱 날짜를 확인하고 `7일`이 경과했으면 해당 실행에서 전체 비중 조정을 수행한다.
- 신규 글이 없는 `scheduled` 실행도 조기 종료하지 않는다. 포트폴리오 판단과 비중은 유지하고
  최신 가격, 수익률, 그래프, HTML, Telegram 메시지를 갱신한다.
- 신규 글이 없는 날의 Telegram은 기존 분석 보고서를 반복 전송하지 않는다. 현재 수익률,
  전일 대비 변화, 포트폴리오 변경 없음, 대시보드 링크를 담은 짧은 성과 요약 메시지를
  전송한다.
- 수동 리밸런싱은 별도 workflow 파일을 만들지 않는다. 기존 Actions의 `Run workflow`
  입력 옵션에서 `rebalance`를 선택하여 즉시 실행할 수 있게 한다.
- `verify`는 실제 Telegram 메시지를 전송한다. 사용자가 실제 수신 결과를 확인할 수 있어야
  한다.
- `verify`는 임시 상태에서 실행하며 실제 포트폴리오 상태, 거래 원장, 성과 이력을 변경하지
  않는다.
- `verify` 결과물은 Actions artifact로도 남겨 HTML과 PNG를 확인할 수 있게 한다.
- `test`는 Gemini API 호출을 전제로 하지 않는다. 로컬에 API 키가 없어도 fixture와 mock
  응답으로 파싱, 상태 전이, 성과 계산, HTML 생성을 검증할 수 있어야 한다.

**완료 조건**

- 모드 이름과 동작이 명확하다.
- 모드별 상태 저장 여부 테스트가 있다.

**구현 완료**

- 운영 진입점을 구조화 판단 JSON, 신규 상태 구조, 모델 거래 원장을 사용하는 흐름으로
  교체했다.
- `adhoc`을 폐기하고 `scheduled`, `rebalance`, `verify`, `test` 정책을 코드로 분리했다.
- 수동 Actions 기본값은 운영 상태를 변경하지 않는 `verify`다. `verify`는 `output/verify`
  임시 폴더에서 실행하고 결과 HTML, PNG, JSON을 artifact로 남긴다.
- `test`는 Gemini와 Telegram을 호출하지 않고 자동 테스트만 실행한다.
- 신규 글이 없는 `scheduled` 실행은 판단과 비중을 유지하고 최신 성과, HTML, PNG, 짧은
  Telegram 성과 요약만 갱신한다.
- Telegram 구조화 요약은 모델 포트폴리오임을 명시하고 종목별 `메르`, `AI`, `미분류`
  판단 주체를 표시한다.
- 최초 정확 추적 실행은 재평가 후 남은 포트폴리오를 기준선으로 삼는다. 과거 거래 가격을
  추정하거나 최초 전환 전에 종료된 종목의 가짜 매도를 만들지 않는다.
- `tests/test_runtime_modes.py`, `tests/test_telegram_summary.py`와 모델 원장 보강 테스트를
  추가했다.
- 검증 결과: `PYTHONUTF8=1 python -m unittest discover -s tests -v` 실행 시 전체 `51`개
  테스트가 통과했고, `RUN_MODE=test python main.py`도 API 키 없이 정상 종료했다.

### 12. 통합 검증 및 배포

**목적:** 변경된 전체 흐름을 실제 환경에서 확인한다.

**검증 범위**

- Gemini 응답 파싱
- 추천 검증
- 상태 파일 갱신
- 성과 추적
- HTML 및 PNG 생성
- Telegram 출력
- GitHub Actions 실행

**합의됨**

운영 반영 전 검증은 개발 브랜치에서 수행한다.

```text
1. 개발 브랜치에서 구현
2. 로컬 test 실행
3. 개발 브랜치 push
4. 개발 브랜치에서 GitHub Actions verify 수동 실행
5. Telegram 실제 수신 결과 확인
6. HTML, PNG Actions artifact 확인
7. 운영 포트폴리오 상태, 거래 원장, 성과 이력이 변경되지 않았는지 확인
8. 문제가 있으면 개발 브랜치에서 수정하고 다시 verify 실행
9. 검증 완료 후 main 반영
10. scheduled 운영 확인
```

`verify`는 운영 상태를 변경하지 않아야 한다. 검증이 끝나기 전까지 `main`의 scheduled 운영은
기존 코드로 계속 동작한다.

**완료 조건**

- 자동 테스트가 통과한다.
- 상태를 훼손하지 않는 방식으로 실제 Actions 결과를 확인한다.
- 검증 결과를 문서에 기록한다.

**검증 진행**

- 개발 브랜치 `codex/mer-ai-portfolio-v2`에서 첫 `verify` Actions 실행을 수행했다.
- 자동 테스트는 통과했지만 실제 분석은 실패했다. 원인은 `gemini-2.5-pro` 무료 할당량이
  `0`이고, fallback `gemini-2.5-flash`가 일시적 `503 UNAVAILABLE`을 반환한 것이다.
- 코드 오류가 아닌 모델 가용성 문제였지만 정상 운영 경로의 호출 수를 줄이기 위해 Actions의
  글별 사전 요약 호출을 끄고 원문을 최종 분석에 바로 전달하도록 했다.
- 기본 분석 모델은 `gemini-2.5-flash`, fallback은 안정 버전 `gemini-2.5-flash-lite`로
  조정했다.
- 두 번째 `verify`에서는 `gemini-2.5-flash-lite`가 1차 판단 JSON을 정상 생성했다.
  2차 보고서도 생성됐지만 `인사이트`라는 제목 문자열이 없다는 이유로 형식 검사가 전체
  실행을 폐기했다.
- 사용자에게 필요한 결과는 제목 문자열이 아니라 모델 포트폴리오 내용이므로, 보고서
  프롬프트에 권장 섹션을 명시하고 필수 검사는 포트폴리오 섹션 존재 여부로 조정했다.
- 세 번째 `verify`에서는 `gemini-2.5-flash-lite`의 1차 판단 JSON에 비중 변경 종목의 근거
  글이 누락되어 검증이 차단됐다. 근거 없는 변경을 통과시키지 않고, 검증 오류를 모델에
  전달하여 같은 단계 전체 응답을 한 번 교정하도록 보완했다.
- 네 번째 `verify`에서는 판단 JSON과 보고서가 생성됐지만 상장 코드가 없는 `알레르망`이
  포트폴리오에 포함되어 가격 조회에서 차단됐다. 주식과 ETF 포트폴리오 판단은 상장 코드
  또는 티커가 반드시 있어야 하며, 비상장 기업과 코드가 불명확한 대상은 Watchlist로
  분류하도록 검증과 프롬프트를 강화했다.
- 다섯 번째 `verify`에서는 상장 코드 누락 검증과 교정이 앞단에서 동작했다. 첫 누락 항목은
  교정됐지만 다른 누락 항목이 남았으므로, 전체 응답 교정을 최대 두 번 수행한 뒤에도
  잘못된 경우에만 실행을 차단하도록 보완했다.
- 여섯 번째 `verify`에서도 모델이 동일한 비상장 후보를 빈 코드와 `null` 코드로 반복
  제안했다. 상장 코드가 없는 주식과 ETF 제안은 포트폴리오에 반영하지 않고 로그에 남긴 뒤,
  나머지 검증된 판단만 반영하도록 보완했다.
- 일곱 번째 `verify`에서는 비상장 후보 제외 후 보고서까지 생성됐지만, 기존 포트폴리오
  비중을 유지한 채 신규 매수 비중을 더해 현금보다 큰 주문이 생성됐다. 1차 판단을 기존
  상태에 적용한 최종 목표 비중 합계가 `100%`를 넘으면 보고서를 만들기 전에 차단하고,
  검증 오류를 모델에 전달하여 적용 가능한 전체 판단으로 교정하도록 보완했다. 현금은 별도
  종목이 아니라 잔여 비중임을 프롬프트에도 명시했다.
- 여덟 번째 `verify`에서는 비중 검증을 통과했지만 `두산로보틱스`에 실제 조회 불가능한
  종목 코드가 붙어 가격 조회에서 차단됐다. 코드 문자열 존재 여부뿐 아니라 실제 현재 가격
  조회 가능 여부도 보고서 생성 전에 검사하고, 실패 시 1차 판단 교정으로 되돌리도록
  보완했다. 실패한 `verify`도 오류 로그를 artifact로 확인할 수 있게 업로드 조건을
  조정했다.
- 아홉 번째 `verify`에서는 가격 조회 검증이 보고서 생성 전에 동작했다. 다만 모델이 교정
  과정에서도 `알레르망`, `두산`에 조회 불가능한 코드를 반복 제안했다. 신규 제안은 가격을
  확인할 수 없는 경우 포트폴리오에서 제외하고 나머지 검증된 판단만 보고서에 반영하도록
  조정했다. 기존 보유 종목의 가격 조회 실패는 조용히 제외하지 않고 계속 실행을 차단한다.
- 열 번째 `verify`에서는 Actions 분석, Telegram 전송, HTML 및 PNG artifact 생성까지
  성공했다. HTML과 구조화 상태는 정상이나 PNG만 기존 Markdown 표 파서를 사용해 추천
  비중을 표시하지 못했다. PNG도 HTML과 동일한 구조화 상태에서 종목 목표 비중과 잔여 현금
  비중을 읽도록 조정했다. 첫 성과 지점이 `0.0%`일 때 라벨 위치 때문에 PNG 위쪽에 큰
  여백이 생기는 문제도 함께 정리했다.
- 열한 번째 `verify`에서는 PNG 보완 코드가 포함된 상태로 자동 테스트까지 통과했다.
  실제 분석에서 조회 불가능 신규 후보 제외도 정상 동작했으나, 남은 목표 비중 합계가
  `113%`여서 모델 교정을 요청하는 시점에 `gemini-2.5-flash-lite` 무료 일일 요청 한도
  `20`회를 모두 사용했다. `429 RESOURCE_EXHAUSTED`로 실제 Actions 재검증은 다음 할당량
  갱신 이후 이어서 수행해야 한다. 열 번째 성공 artifact 상태를 사용한 로컬 PNG 렌더링은
  종목 10개, 현금 `16%`, 수익률 `0.0%`를 정상 표시하는 것을 확인했다.
- 다음 할당량 갱신 후 수행한 열두 번째 `verify`에서는 Actions, Telegram 전송, PNG
  artifact 생성까지 성공했고 PNG도 종목 10개와 현금 `16%`를 정상 표시했다. 구조화 상태도
  목표 비중 합계 `84%`, 원장 현금 `16%`로 일치했다. 다만 Gemini 보고서가 포트폴리오 표
  헤더에서 불필요한 공백을 대량 출력한 뒤 잘려 HTML 전체 보고서가 비정상적으로 커졌다.
  보고서는 네 개 사용자용 섹션이 끝까지 존재하고 비정상적으로 긴 전체 길이 또는 단일 줄이
  없어야 통과하도록 검증을 강화했다. 보고서 프롬프트에도 간결한 표와 불필요한 공백 금지를
  명시했다.
- 보고서 품질 검증 보완 후 수행한 열세 번째 `verify`는
  `gemini-2.5-flash-lite` 무료 일일 요청 한도 `20`회 소진으로 1차 판단 호출 전에
  `429 RESOURCE_EXHAUSTED`가 발생했다. 동일한 개발 브랜치에서 기본 모델
  `gemini-2.5-flash`로 실제 검증을 이어서 수행한다.
- 이어서 수행한 열네 번째 `verify`에서는 `gemini-2.5-flash`도 무료 일일 요청 한도
  `20`회를 소진한 상태임을 확인했다. fallback `gemini-2.5-flash-lite`가 1차 판단을
  반환했으나 2차 사용자용 보고서 호출 시점에는 두 모델 모두
  `429 RESOURCE_EXHAUSTED`가 발생했다. Google 공식 문서상 일일 요청 한도는 태평양 시간
  자정에 갱신되므로, 실제 HTML 보고서 재검증은 다음 갱신 이후 이어서 수행한다.

### 13. Gemini 모델 역할 정책 복원

**목적:** 투자 판단 품질에 직접 영향을 주는 Gemini 모델 역할을 기존 운영 의도에 맞게
복원하고, 구조화된 2단계 호출에서 각 모델의 책임을 명확히 한다.

**과거 운영 문서에서 확인했으나 25번에서 투자 판단에는 폐기한 정책**

| 작업 | 모델 |
|---|---|
| 글별 1차 요약 | `gemini-2.5-flash` |
| 최종 투자 분석 | `gemini-2.5-pro` 우선 |
| 최종 투자 분석 fallback | `gemini-2.5-flash`였으나 25번에서 투자 판단에는 사용하지 않기로 변경 |
| `flash-lite` | 품질 저하 우려로 기본 경로에서 사용하지 않음 |

**폐기 예정인 미합의 변경**

- 통합 검증 중 quota 대응을 이유로 최종 분석 기본 모델을 `gemini-2.5-flash`, fallback을
  `gemini-2.5-flash-lite`로 바꾼 변경은 사용자와 합의하지 않은 정책 변경이다.
- 글별 1차 요약 모델을 `gemini-2.5-flash-lite`로 바꾼 변경도 사용자와 합의하지 않았다.
- Actions에서 글별 1차 요약을 항상 끈 변경은 검증 실행의 호출 수를 줄이기 위한 임시
  조정이었다. 정상 운영 정책으로 확정하지 않는다.

**합의됨**

| 작업 | 모델 |
|---|---|
| 글별 1차 요약 | `gemini-2.5-flash` |
| 1차 포트폴리오 판단 JSON | `gemini-2.5-pro` 전용 |
| 2차 사용자용 Markdown 보고서 | `gemini-2.5-pro` 우선 |
| 2차 보고서 fallback | `gemini-2.5-flash` 또는 구조화 판단 기반 결정적 보고서 |
| `gemini-2.5-flash-lite` | 정상 경로에서 사용하지 않음 |

  바탕으로 사람이 읽는 핵심 인사이트를 작성하므로 기존 보고서 품질을 유지하기 위해
  `gemini-2.5-pro`를 사용한다.
- 정상 분석 경로는 `pro` 호출 `2회`다. HTML, PNG, Telegram은 추가 LLM 호출 없이 검증된

- 1차 포트폴리오 판단은 투자 판단 품질에 직접 영향을 주므로 `flash`로 대체하지 않는다.
  Gemini Pro가 서버 혼잡으로 응답하지 않으면 5분 간격으로 5회 더 재시도하고, 그래도 실패하면

- 2차 사용자용 보고서는 검증된 판단 JSON 이후의 설명 단계다. Pro 또는 fallback 호출이 실패해도
  구조화 판단 기반 결정적 Markdown 보고서로 사용자 출력은 계속 생성한다.
- 글별 1차 요약은 기존 정책대로 `flash`를 사용한다. 이미 생성된 요약 캐시는 재사용한다.

  경로를 확인할 quota를 보존한다.

### 14. 일별 수집, 주간 리밸런싱 및 사용자 보고서 정책 복원

**목적:** 매일 수집과 주간(`7일`) 리밸런싱의 역할을 분리하고, 블로그 근거를 보존한 투자 판단과
사용자용 핵심 인사이트를 안정적으로 제공한다.

**합의됨: 수집 및 글별 요약**

- `scheduled`는 매일 `1회` 실행하여 신규 글을 수집한다.
- 원문은 고정 글자 수로 자르지 않고 `posts_db.json`에 저장한다.
- 신규 글은 모두 `gemini-2.5-flash`로 글별 요약한다. 실행당 요약 호출 수 상한은 두지 않는다.
- 글별 요약은 투자 관련 여부, 분류 이유, 핵심 사실, 인과관계, 언급 종목과 섹터, 메르 본인의
  직접 투자 발언을 보존한다.
- 맛집, 여행, 일반 건강 등 투자와 무관한 글도 DB에는 저장하지만 Pro 투자 분석 입력에서는
  제외한다. 제목 키워드가 아니라 본문 문맥으로 분류한다.
- 저장 원문은 유지한다. API 요청 토큰을 확인하고 모델 입력 한도의 `80%`를 넘는 비정상적인
  요청에만 전송용 본문의 끝부분을 줄인다.
- 최초 전환 시 최근 `14일` 글만 원문을 다시 수집하고 새 형식 Flash 요약으로 갱신한다.
  전체 과거 DB는 재처리하지 않는다.

**합의됨: 일별 분석 및 리밸런싱**

- 관련 신규 글이 있으면 해당 신규 글 묶음으로 Pro를 `2회` 호출한다.
  1. 구조화 포트폴리오 판단 JSON
  2. 검증된 판단 JSON과 글 요약을 바탕으로 한 사용자용 Markdown 보고서
- HTML, PNG, Telegram 생성에는 추가 LLM 호출을 사용하지 않는다.
- 관련 신규 글이 없으면 판단과 비중을 바꾸지 않고 가격, 성과, HTML, PNG, 짧은 Telegram
  성과 메시지만 갱신한다.
- 마지막 실제 리밸런싱 이후 `7일`이 지나면 그 이후 누적된 투자 관련 글 전체와 현재 상태로
  리밸런싱한다.
- `7일`이 지났어도 관련 신규 글이 없으면 리밸런싱을 연기한다. `last_rebalanced_date`를
  갱신하지 않고 다음 관련 글이 들어온 날 실행한다.
- 리밸런싱 입력이 없을 때 최근 `30일` 글을 다시 읽는 fallback은 사용하지 않는다.

**합의됨: AI 편입과 Watchlist**

- 메르 본인이 특정 종목의 매수, 보유, 매도를 밝혔다고 LLM이 문맥상 판정한 경우만
  `메르 직접 발언`으로 표시한다.
- 원문에 직접 등장한 종목도 방향성 있는 투자 논리, 현재 편입 이유, 주요 위험, 근거 글을
  모두 제시해야 `AI 제안`으로 모델 포트폴리오 편입 후보가 될 수 있다.
- 단순 사례, 비교 대상, 뉴스 나열로 등장한 종목은 즉시 편입하지 않고 Watchlist로 보낸다.
- 원문에 특정 종목명이 없고 섹터 논리만 있으면 AI가 추론한 개별 종목은 Watchlist만 허용한다.
- 원문에 없는 섹터 ETF는 예외적으로 조건부 편입 후보가 될 수 있다. 섹터 논리, 대표성,
  현재 편입 이유, 주요 위험을 모두 기록해야 한다.
- Watchlist는 비중과 성과 계산에서 제외한다. 이후 새 근거가 강해지면 모델 포트폴리오로
  이동할 수 있다.

**합의됨: 핵심 인사이트와 사용자 출력**

- 핵심 인사이트는 1차 Pro 판단 JSON에서 구조화한다.
- 신규 매수, 매도, 비중 변경에는 연결된 핵심 인사이트가 반드시 있어야 한다.
- 섹터 온도계는 제거한다. 섹터 분석은 근거 글 URL과 투자 시사점이 있는 핵심 인사이트로
  제공한다.
- Telegram과 HTML은 핵심 인사이트 개수를 임의로 줄이지 않는다.
- Telegram은 인사이트별 제목, 짧은 요약, 투자 시사점을 표시한다. 전체 메시지가 `4,000자`를
  넘으면 같은 양식을 유지한 채 여러 메시지로 나누고, 뒤를 잘라내지 않는다.
- 모델 포트폴리오는 하나로 유지한다. 각 종목은 `메르 직접 발언` 또는 `AI 제안` 출처와
  행동, 비중, 짧은 이유를 표시한다.
- Watchlist는 모델 포트폴리오와 별도 영역으로 표시한다.
- `[AI] Alcoa`처럼 출처를 종목명 앞 접두사로 표시하지 않는다.
- HTML 상단에는 전체 핵심 인사이트를 표시한다. 종목 상세에는 판단일, 출처, 근거 유형,
  원문 등장 여부, 변경 이유, 근거 글 제목, 게시일, URL을 제공한다.
- HTML의 목표 비중 그래프와 Telegram PNG 그래프는 같은 전체 모델 포트폴리오 상태를
  원천으로 사용하고, 같은 도넛 그래프 형식으로 표시한다.
- Telegram 텍스트 메시지는 포트폴리오 변경 여부와 관계없이 모델 포트폴리오 수익률을
  표시한다.
- 2차 사용자용 Markdown 보고서 LLM 호출이 quota, timeout, 서버 오류로 실패하더라도
  검증된 1차 판단 JSON과 변경 반영 후 전체 상태로 결정적 Markdown 보고서를 생성해
  HTML, PNG, Telegram 발송 경로를 계속 진행한다.
- 1차 포트폴리오 판단 LLM 호출이 quota, timeout, 서버 오류로 실패하면 새 투자 판단을
  임의로 만들지 않는다. 기존 포트폴리오 상태와 기존 보고서를 유지하고 성과, HTML, PNG,
  Telegram을 갱신하되, Telegram에는 `LLM 한도 초과 또는 일시 장애로 신규 글 분석 보류`를
  표시한다.

**합의됨: 구조화 판단 응답 크기 관리**

- 1차 판단 JSON은 전체 포트폴리오와 전체 Watchlist 복사본이 아니라 이번 입력 글에 따른
  변경분만 출력한다.
- 기존 종목의 판단과 비중이 그대로 유지되면 `보유` 항목을 반복 출력하지 않는다. 이번 글에
  메르의 직접 보유 발언 또는 기존 판단을 실질적으로 갱신하는 새 근거가 있을 때만 `보유`
  변경분을 기록한다.
- Watchlist도 이번 글로 추가, 갱신, 종료하는 항목만 출력한다.
- 생략된 기존 포트폴리오와 Watchlist 항목은 코드가 유지한다.
- 사용자용 Markdown 보고서는 검증된 변경분과 변경 반영 후 전체 상태를 함께 받아 현재
  포트폴리오와 Watchlist를 빠뜨리지 않고 표시한다.

### 15. scheduled 글별 Flash 요약 JSON 실패 보류 처리 및 진단 개선

**목적:** scheduled 실행에서 신규 글별 Flash 요약 응답이 잘리거나 깨졌을 때 전체 Actions를
중단하지 않고, 해당 글만 투자 분석 대상에서 보류한 뒤 다음 실행에서 재시도한다.

**확인된 원인**

- scheduled 실행 `27067157733`은 main 커밋 `3e25c8c`에서 실행됐다.
- 신규 글 `코스트코와 이마트 트레이더스의 비밀(feat 97헌터)` 수집 후 글별 Flash 요약 단계에서
  `JSONDecodeError: Unterminated string`이 발생했다.
- 기존 `_parse_summary_response`는 Gemini 응답을 그대로 `json.loads`했고, `_summary_fields`와
  `_refresh_recent_summary_cache`가 예외를 처리하지 않아 신규 글 저장 전 전체 수집이 중단됐다.
- 이 실패는 포트폴리오 Pro 판단이나 HTML/Telegram 출력 단계가 아니라 글별 1차 요약 캐시 단계의
  응답 형식 실패다.

**합의됨**

- 정상 경로를 먼저 강화한다. 글별 요약 요청은 JSON 스키마, JSON 전용 응답, 요약 길이 제한,
  충분한 출력 토큰을 사용한다.
- 그래도 응답이 비거나 JSON이 깨진 경우 해당 글은 `summary_status: deferred`로 저장한다.
- 보류 글은 `investment_relevant: false`, `summary_version: null`로 저장해 Pro 투자 판단 입력에서
  제외하고 다음 scheduled/rebalance 실행에서 다시 요약한다.
- 보류 글이 있으면 Telegram과 HTML의 사용자 출력에 보류 건수와 글 제목을 표시한다. 중요한 글이
  조용히 빠진 것처럼 보이면 안 된다.
- API 키 미설정 같은 구성 오류는 보류로 숨기지 않고 실행 실패로 둔다.
- scheduled 실패 시에는 최소 진단 artifact를 업로드해 Telegram 실패 알림만 보고 원인을 추정하지
  않게 한다.

**완료 조건**

### 17. 종료 포지션과 현재 추천 중복 제거 및 Telegram 추천 형식 간소화

**목적:** 투자자가 보는 화면에서 같은 종목이 현재 추천과 종료 포지션에 동시에 보이지 않게 한다.
Telegram 추천 목록은 세부 분석이 아니라 빠른 확인용 요약으로 유지한다.

**확인된 문제**

- 대한전선은 현재 모델 포트폴리오 상태에는 `보유`로 남아 있지만, 수익률 계산 자료의
  `closed_positions`에는 과거 `현재 포트폴리오에서 제외` 기록이 남아 있다.
- 사용자가 보는 출력에서 현재 추천과 최근 종료 포지션이 함께 보이면 같은 종목을 보유하라는
  것인지 종료했다는 것인지 알 수 없다.
- Telegram 추천 목록이 판단 주체, 수익률, 변경 이유까지 표시해 메시지가 과해졌다. 세부 내용은
  HTML에서 확인하면 된다.

**합의됨**

- 현재 모델 포트폴리오에 있는 종목은 사용자 출력의 종료 포지션에 표시하지 않는다.
- 수익률 계산 자료에 과거 종료 기록이 남아 있어도 현재 포트폴리오 상태가 우선이다.
- Telegram 국내주식 추천은 `종목명 — 판단 (비중)` 형식으로 표시한다.
- Telegram 해외주식 추천은 `종목명 (티커) — 판단 (비중)` 형식으로 표시한다.
- Telegram 추천 목록에는 판단 주체, 수익률, 변경 이유를 붙이지 않는다. 그 세부 내용은 HTML에서
  확인한다.

**완료 조건**

### 21. 과거 포트폴리오 `allocation_role` 백필 및 신규 AI 판단 역할 검증 강화

**목적:** 20번에서 새로 도입한 포트폴리오 역할 필드가 과거 상태 파일에는 없어, 기존 보유 종목이

- 백필된 역할은 이후 리밸런싱에서 최신 근거에 따라 바뀔 수 있다.
- 과거 `decision_history`에도 근거가 없는 `미분류` 포지션은 역할만 백필하고, 판단 주체를 AI로
  임의 승격하지 않는다.
- 앞으로 AI가 신규 매수뿐 아니라 보유, 비중확대, 비중축소를 판단할 때도 `allocation_role`을
  반드시 채워야 한다.
- 현재 포트폴리오에 역할이 비어 있는 종목이 있으면 LLM은 변경이 없더라도 `보유` 판단으로 역할을
  보강해야 한다.

**완료 조건**

- `output/portfolio_state.json`의 현재 보유 포지션에 `allocation_role`이 채워진다.

- Telegram/HTML/Markdown 추천 목록에 기존 보유 종목이 역할 누락 때문에 전부 빠지지 않는다.

### 23. 검증 모드 Telegram 링크와 운영 HTML 불일치 수정

**목적:** `verify`/`full_verify`가 운영 파일을 덮어쓰지 않는데도 Telegram 메시지에 운영
대시보드 링크를 넣어, 검증 결과와 사용자가 누른 HTML이 서로 다르게 보이는 문제를 제거한다.

**확인된 문제**

- `full_verify` artifact의 `output/full_verify/dashboard.html`에서는 LS, 대한전선, 현대차가
  `AI 제안 · 보유`로 정상 표시됐다.
- 그러나 Telegram의 `대시보드 전체 보기` 링크는 GitHub Pages의 운영 `output/dashboard.html`을
  가리켰고, 이 운영 HTML은 이전 실행 결과라 `미분류 · 보유`가 남아 있었다.
- 따라서 검증 메시지와 링크된 HTML이 서로 다른 기준 자료처럼 보였다.

**합의됨**

- 운영 파일을 덮어쓰지 않는 `verify`/`full_verify`에서는 Telegram 구조화 요약에 운영 대시보드
  링크를 넣지 않는다.
- 검증 모드 메시지에는 HTML이 GitHub Actions artifact에 저장된다는 안내를 표시한다.
- 운영용 `output/dashboard.html`은 현재 `output/portfolio_state.json` 기준으로 재생성해

### 25. Gemini Pro 서버 혼잡 시 투자 판단 보류 정책

**목적:** 투자 판단 품질을 낮추는 임시 대체 모델 사용을 막고, Gemini Pro가 일시적으로 응답하지
않는 경우에는 새 매수/매도/비중 판단을 만들지 않고 기존 포트폴리오를 유지한다.

**확인된 문제**

- 2026-06-15 운영 리밸런싱에서 Gemini Pro가 서버 혼잡으로 응답하지 않았고, Flash가 대신 1차
  포트폴리오 판단을 완료했다.
- 이 결과는 현금성 20% 기준을 충족했지만, 투자 판단 단계가 합의한 고품질 모델이 아니라 대체
  모델에서 나온 판단이라는 문제가 있다.
- 투자자가 보는 결과에서는 왜 판단 품질이 달라졌는지 알 수 없으므로, 같은 상황이 다시 생기면
  비중을 바꾸지 않고 보류 사유를 명확히 보여야 한다.

**합의됨**

- 글별 1차 요약은 기존대로 `gemini-2.5-flash`를 사용할 수 있다.
- 1차 포트폴리오 판단 JSON은 `gemini-2.5-pro` 전용이다. `GEMINI_MODEL`이 Flash로 지정되어도
  투자 판단 단계에는 Pro 계열 모델만 사용한다.
- Gemini Pro가 서버 혼잡으로 응답하지 않으면 5분 간격으로 5회 더 재시도한다. 최초 시도까지
  합쳐 총 6회다.
- 총 6회 뒤에도 응답하지 않으면 Flash로 투자 판단을 대체하지 않는다.
- 이 경우 기존 포트폴리오와 목표 비중을 유지하고, 사용자 출력에

  않고 기존 포트폴리오와 목표 비중을 유지한다.
- 2차 사용자용 Markdown 보고서는 이미 검증된 판단 이후의 설명 단계이므로, Pro 보고서 호출이
  실패하면 구조화 판단 기반 결정적 보고서로 사용자 출력 생성을 계속한다.

**완료 조건**

## 31. GitHub Actions 전달 순서와 운영 리밸런싱 정상화

**목적:** 메르 추종 모델의 상태·리포트·Telegram 알림이 서로 다른 실행 결과를 가리키지 않도록 한다. 정기 자동 메시지와 리포트는 이 프로젝트의 핵심 산출물이며, 투자 판단보다 먼저 전달 신뢰성을 보장한다.

**구현 계약:**

- 기존 `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`와 동일한 봇을 유지한다.
- `scheduled`/`rebalance`는 상태와 보고서를 생성한 뒤 현재 `GITHUB_RUN_ID`가 적힌 `run_status.json`을 남긴다.
- workflow는 영수증·출력 경로를 검증하고 `output/`을 commit/push한 뒤에만 차트와 구조화 Telegram 요약을 보낸다.
- Telegram 성공은 HTTP 상태만이 아니라 JSON `ok=true`, `result.message_id`까지 확인한다. 수락되지 않은 차트 또는 요약이 하나라도 있으면 Action은 실패하고 진단 artifact를 남긴다.
- v2.0 상태의 이전 리밸런싱 날짜는 완전 커버리지·출처 검증을 증명하지 못하므로 초기화한다. 최근 요약의 v4 업그레이드가 진행 중이면 부분 리밸런싱을 하지 않고, 완료된 범위에서 한 번의 전체 리밸런싱을 수행한다.
- API 보류 상태에서도 매수·매도·목표비중은 바꾸지 않지만, 만료 Watchlist는 관찰 수명주기상 archive한다.

**완료 조건:**

- 정기 실행은 00:17 KST로 예약되고 동시 실행 없이 `main`에서만 운영 상태를 갱신한다.
- Action 로그에서 `persist` 성공 뒤 Telegram 차트와 구조화 요약의 수락 message ID를 확인할 수 있다.
- push 실패 시 Telegram 운영 리포트가 발송되지 않으며, Telegram 거절 시 원격 상태는 보존되지만 Action은 녹색으로 끝나지 않는다.
- 출처 버전이 오래된 글 또는 불완전한 과거 리밸런싱이 새로운 메르 판단처럼 포트폴리오에 반영되지 않는다.

  사용하며 단순 언급 10, 이벤트 20, 경기·공급망 60, 구조적 thesis 120거래일을 기본 만기로 둔다.
- 주간 리밸런싱은 전 종목의 실제 NAV 비중을 계산하고 50bp 이상 차이를 거래한다. 전 종목
  검토와 거래 후 10bp 이내 정합성이 확인된 경우에만 리밸런싱 날짜를 갱신한다.
- 일반 거래는 실제 NAV 대비 종목별 목표 차이의 절댓값 합을 총 거래 명목으로 정의하고 실행당
  15%로 제한한다. MDD·변동성에 따른 강제 위험 축소, 전량 청산과 명시적 논지 무효화,
  패시브 슬리브 최초 편입 및 그 재원 매도는 즉시 실행해야 하므로 이 한도를 소비하지 않는다.
- 종목 한도는 메르 5%, AI 2%, 발행사 5%, 테마 15%, 국가 55%다. 적격 신호가 부족한
  슬리브의 잔여 비중은 현금으로 둔다.
- 성과는 깨끗한 신규 원장에서 비용·환율·현금·배당·분할을 추적하고
  `KOSPI200 TR 40% + S&P500 TR(KRW) 40% + 현금 20%`를 고정 벤치마크로 비교한다.
