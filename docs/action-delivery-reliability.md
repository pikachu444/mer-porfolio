# GitHub Actions 전달·운영 신뢰성

이 프로젝트의 운영 산출물은 모델 포트폴리오 상태, Markdown/HTML/PNG 리포트, Telegram 알림이다. 자동 실행이 녹색이라는 사실만으로 사용자에게 리포트가 전달되었다고 판단하지 않는다.

## 정기 실행 계약

- 정기 실행은 매일 00:17 KST(UTC 15:17)에 시작한다. GitHub Actions의 정각 지연 가능성을 피하기 위해 정각 cron을 사용하지 않는다.
- `scheduled`와 `rebalance`는 `main` 브랜치에서만 상태를 변경한다. 동시 실행은 직렬화하고, 외부 API 호출을 포함한 작업은 30분 안에 끝나도록 제한한다.
- 기존 `TELEGRAM_BOT_TOKEN`과 `TELEGRAM_CHAT_ID`를 그대로 사용한다. 봇을 교체하거나 토큰을 로그에 남기지 않는다.

## 저장 후 발송 순서

운영 리포트는 아래 순서로만 발송한다.

```text
수집·검증·판단
  → 상태/리포트/차트 생성
  → run_status.json으로 현재 Action의 안전한 산출물 확인
  → output 커밋·push 성공
  → Telegram 차트와 구조화 요약 발송
```

따라서 Git push가 실패한 실행은 Telegram 운영 리포트를 먼저 보내지 않는다. 반대로 Telegram 전송이 거절되면 이미 안전하게 저장된 상태는 보존하되 Action을 실패로 표시하고 진단 artifact를 남긴다. 다음 예약 실행이 이전 상태를 다시 판단하는 일을 막기 위한 규칙이다.

Telegram 성공은 HTTP 200만으로 판단하지 않는다. Telegram JSON 응답의 `ok=true`와 실제 `message_id`를 모두 확인해야 성공으로 기록한다. 로그에는 채팅 대상의 단방향 SHA-256 지문과 message ID만 남기며, chat ID·봇 토큰·원문 응답은 남기지 않는다.

## 운영 모드

| 모드 | 상태 저장 | Gemini 호출 | Telegram |
|---|---:|---:|---|
| `scheduled` | 예 | 필요 시 | 저장·push 뒤 발송 |
| `rebalance` | 예 | 예 | 저장·push 뒤 발송 |
| `verify` | 아니오 | 아니오 | 현재 상태 기준으로 즉시 검증 발송 |
| `full_verify` | 아니오 | 예 | 격리된 검증 출력 기준 발송 |
| `test` | 아니오 | 아니오 | 발송 안 함 |

`verify`는 실제 봇·chat 설정을 바꾸지 않고 Telegram 도착 계약을 점검하는 용도다. 로그에 수락된 message ID가 있는데도 사용자가 받지 못하면, 봇 자체가 아니라 `TELEGRAM_CHAT_ID`가 다른 채팅을 가리키거나 해당 채팅에서 봇이 차단·음소거된 상태인지 확인한다.

## 메르 추종 데이터 안전장치

과거 요약 스키마(v2)는 원문 exact span 검증과 신호 출처가 없으므로 새 메르 신호처럼 사용하지 않는다. 최근 14일의 과거 캐시는 한 실행에 제한된 수만 업그레이드하며, 그 작업이 끝나기 전에는 전체 리밸런싱을 보류한다. 기존 v2.0의 불완전한 리밸런싱 기준일은 신뢰하지 않고, 업그레이드가 끝난 뒤 출처가 검증된 전체 범위로 한 번의 완전 리밸런싱을 수행한다.

요약 또는 Gemini 판단이 보류되면 매수·매도·목표비중 변경은 하지 않는다. 다만 만료된 Watchlist 관찰 항목은 투자 판단과 독립적인 수명주기 정리이므로 계속 archive한다.
